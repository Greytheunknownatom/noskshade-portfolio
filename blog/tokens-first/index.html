Design systems

I built my first design system backwards. Here’s what I’d do instead.

I started with buttons and cards. Three weeks later I had three versions of every button and a developer who had stopped asking me questions.

Philip Nosike · 28 October 2026 · 5 min read

Three products. One small team. One deadline that didn’t care about either.

I did what felt natural: I designed the components first. Buttons, cards, inputs. Beautiful ones.

Then the admin dashboard needed tighter tables. The mobile app needed bigger tap areas. Every “small exception” created a new version of something.

Within a few weeks the system wasn’t a system. It was a collection.

The fix was making decisions before shapes

I went back and started with tokens: the small, named decisions underneath everything. Which colour means “do this.” How much space sits between related things. How big a heading is.

Each product could then use those same decisions at its own size. Same language, different density.

If a developer has to ask which grey to use, the system has already let them down.

Two mistakes I won’t repeat

  • Naming things by how they look (“blue-500”) instead of what they do (“action-primary”). One brand change meant editing hundreds of layers.
  • Writing the documentation in a separate file nobody opened. Notes inside the components did more than any handbook.

If you’re starting a system this month, start smaller than feels right. Ten good decisions beat a hundred pretty components.
